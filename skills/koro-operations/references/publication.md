# 发布计划、真实执行与恢复

先明确本次账号范围、品类、条数、选片和预约时区。已有授权和偏好持续有效；只补问实际缺失的信息。按用户需求拟标题、标签和吸睛封面，保存选择依据。平台要求与可选设置分别处理，不擅改用户无关设置。

## 本地预检

发布请求为JSON：

```json
{
  "items": [{
    "work_id": "sample-work-01",
    "account_id": "sample-account-a",
    "title_en": "A tiny delivery 📦",
    "hashtags": ["#cute", "#funny"],
    "cover": "选择正脸与包裹同框、动作清晰的帧",
    "scheduled_at": "2099-10-20T00:00:00+08:00"
  }]
}
```

示例未来日期仅展示格式，实际日期必须按用户意图填写。即时发布不填scheduled_at。标题标签可覆盖作品默认；可用sha256指定期待版本。多角色通过账号allowed_roles明确允许的完整角色分类。

plan核对稳定作品/账号ID、交付状态、当前文件、指纹、品类、禁用/退出观察、历史任务、请求内重复和带时区的未来预约时间。候选作品的记录错误阻止计划；无关历史作品的错误仍以outside_request警告报告，不要求为发布一条新片先修复全部旧工程。失败/跳过/取消的历史任务不占用；其他已提交、已预约、结果未知和无法识别的状态保守阻止同账号重发。结果未知需先查平台，不能直接将其改成失败来重试。同文件以不同作品名出现在同一账号计划中也阻止。

输出中的proposed是建议计划，`reserved:false`意味着尚未占用视频。多个聊天的plan都可能通过；真正提交前必须由执行层串行核对并持久化占用/任务状态。第一版没有实现跨进程预约锁或平台执行器，不能声称plan防止了并发提交。

## 真实执行

实际发布使用本机已有且已验证的魔云腾MCP/官方接口、比特浏览器连接或当前可用的UI能力。没有连接时交付计划并说明缺失连接，不把请求交给不存在的插件工具。完整容器ID、设备及当前TikTok用户名要核对一致；同坑位不同后缀是不同云机。切换后重新核对身份，完成时按任务需要恢复原云机。

在授权范围内上传指定版本，填写文案并选封面，核对账号、日期、时区和可见性再提交。提交后保存作品页/预约列表、可得的作品ID/链接、截图和观察时间。按钮点击成功、上传完成、自动化返回ok都不能单独证明已发布。

连接中断或提交响应丢失时记录“结果待核实”，先查平台实际结果。未提交且账号已退出的任务可跳过、释放并重新分配；已提交但未知的任务暂不释放。不得自动重登、改账号身份或扩大授权范围。

## 记录与展示

每次发布分配有独立publication_id，关联work_id、账号稳定ID、选定文件SHA256、文案/封面、计划时间、实际提交/核验时间及证据。作品可发布到多个账号，每个账号的任务独立。

旧记录兼容items/videos数组、work_id或work:前缀record_id，以及父级账号字段。预检读取原记录，不迁移或改写。目录预标记保留原始依据；不能把它写成平台实发核验。

用户选择预约成功即可在台账显示已发布时，按本地display.scheduled_counts_as_published展示；底层仍记录scheduled及原预约时间。该显示偏好不是到点后平台成功的证据。第一版不自动写回Excel，按已有build.mjs/发布标记机制执行用户要求的回填，保留手动字段和冲突信息。
